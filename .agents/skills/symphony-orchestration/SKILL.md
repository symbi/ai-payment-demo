# Symphony 持续补位调度

目标：在现有授权、依赖、资源和写入边界内持续推进就绪任务，避免“必须整批完成才能开下一批”的人为等待。复用现有 tracker、工作记录和原生观测面板，不建立新管理平台，也不为凑并发拆出无价值任务。

## 先判断自己的角色

- **主控／调度者**：负责队列、就绪判断、领取范围、文件交接、集成和补位。
- **实现 Worker**：只完成交给自己的固定任务包，保存产物及实际检查结果，交接后停止。不自行领取下一张卡、扩大权限或启动子 Agent。
- **验收 Worker**：验证固定集成版本；是否可修复由本任务授权决定。测试通过、技术验收通过、用户验收和发布是不同状态。

如任务包已指定角色、范围和工作流，直接复用，不重复做一次 intake、试安装或整套规划。本 Skill 是调度约定，不替代现有实现／验收契约。

## 使用项目真实设置

启动或恢复时，读取项目 AGENTS、已有交接记录，以及**当前实际加载**的 WORKFLOW 或等价配置。确认：

- 任务源、明确可领取集合、汇总卡排除规则、当前所有 owner（含其他窗口和机器）。
- 有效并发上限、实际可用模型、资源容量、工作目录、单次执行及重试／停止约束。
- 固定代码基线、输入契约和每项允许写入范围；生产者与消费者需要哪一种交接证据。
- 本机网络和外部动作授权。另一台机器的权限、凭据或已安装工具不能照搬。

并发上限、Issue 编号、模型版本、时限和扫描额度属于项目配置，不能硬编码成通用默认值。缺少影响启动的事实就先核实；不通过提高配置上限、绕过保护或启用新服务填满空位。无需密钥的离线任务不索取密钥。

## 一份可执行队列

复用现有 Issue 摘要或工作记录，每项只需：任务与阶段、交付物、owner／机器、基线与输入、写入范围、依赖与解除证据、模型及理由、状态、最近证据／下一步／更新时间。

状态映射到已有 tracker，无需新增看板：

| 逻辑状态 | 含义 |
| --- | --- |
| Queued | 已登记，尚未完成就绪核对 |
| Blocked | 有具体未满足依赖或限制，并注明负责解除者 |
| Ready | 输入、范围、授权、必要阶段检查和资源已满足，可领取 |
| Running | 已有启动与实际执行证据，不仅是加了标签 |
| Awaiting review | 执行已停止并交付产物，等待指定验收，退出领取范围 |
| Accepted / Done | 已完成约定验收；是否已推送、合并、部署另行报告 |

进程 exit 0 或面板 Running 0 不等于产物已验收。保留真实失败和未运行结果，不编造百分比。标了 Ready 但还没有启动证据时，仍报告 Ready。

## 持续补位循环

在首次调度、任务结束、依赖交接、审批解除或配置允许的轮询点执行：

1. **刷新事实**：从已有 tracker 和运行状态对账，保留已经运行的任务。恢复时先识别已有进程与领取记录，不能再次启动同一任务。
2. **处理结束项**：保存补丁／提交、测试结果、基线、交接记录；确认进程结束，然后通过项目现有流程撤销可领取标记并读回确认。不要在 Worker 写文件时移除会触发终止的标签。若无法撤销且有重复领取风险，停止受影响的领取入口并报告，不破坏其余正在运行的任务。
3. **解除真实依赖**：仅用约定证据释放后续任务。生产者交接稳定接口后，消费者可开始；独立任务无需等待整个里程碑。整体验收必须等所需实现集成到同一固定版本，不能用单个 Worker 完成替代。
4. **选择可运行项**：按用户优先级和项目队列顺序，从 Ready 中筛掉机器不符、重复领取、文件争写、资源不足或缺少必要审批的任务。一个队首任务受阻不应挡住后面的独立 Ready 项。
5. **补空位并核实**：在有效上限内启动合格项，记录实际模型、目录、阶段和启动证据。重负载构建／测试可单独排队，不因此无条件串行化轻量编辑。没有合格项就说明具体原因，不能为填位放松条件。

主控维护下一步就绪性；Symphony 负责按现有适配器领取可执行任务。只有运行证据证明补位链路已实现，才称为自动补位。需要主控释放依赖、切换 phase 或添加 Ready 时，明确说明该职责，不把文档规则等同于已部署自动化。活动工作仍在运行时，不为配置调整盲目重启或杀掉整个调度器。

## 写入隔离、模型与失败

- 一个范围只有一个有效写入 owner。独立 worktree 不能消除同一目标文件的集成冲突；必须固定接口、限定不同文件，或明确先后交接。集成目标由一个主控写入。只读 QA 可检查冻结副本，与下一项独立开发并行。
- 每任务固定自己的阶段及输入清单；若已有全局 phase 造成无必要的整批等待，优先复用配置或做经授权的最小逐任务调整。不能为了并行重写通用调度平台。
- 按任务复杂度和当前可用模型选择：机械文案／目录改动用轻量档，常规联调用中档，状态并发、策略边界或独立复杂验收用高能力档。记录理由，保留显式用户选择；指定模型不可用时报告，不静默降级或切换付费渠道。
- 失败／审批阻塞只阻塞受影响任务；保留证据、错误分类和 owner，继续其他合格任务。遵守既定重试额度；没有新证据不重复同样尝试。配置未授权自动重试时，不重新加 Ready 或清掉执行锁来绕过限制。
- 总目标卡只汇总，不与实现子任务同时被领取。任务完成不等于获得推送、合并、付款或其他外部动作的新授权；复用已明确的适用授权。

## 配置与可移植交接

- 项目 AGENTS 链接本 Skill；Workflow 的 Worker 提示要求读取它并明确角色。并发、标签、hook、目录及网络限制留在项目配置中，不要由通用 Skill 覆盖。
- 另一台机器可直接读取仓库的 `.agents/skills/symphony-orchestration/SKILL.md`，不要求复制全局配置、Memory、插件或凭据。本机全局安装与仓库便携包使用同一版本，更新时同步并核对内容，避免维护两套不同规则。
- 不把历史单任务 Workflow 自动改成通用多任务入口；保留其 disabled、固定任务、并发和审批边界，待具体授权另行升级。

## 汇报与维护

向用户报告实际同时运行的任务及各自交付物，区分排队、运行、待验收和已发布。用启动／结束事件证明重叠，不用“创建了多个 Issue”证明并行；给出下一个可见成果及真实阻塞。

本 Skill 带有 `evals/eval.yaml`，由现有 `skill-upper` / `skill-up` 维护，无需另建技能注册表。修改调度规则时，验证补位、真实依赖、争写、停止重领、模型缺失与机器边界案例。`skill-up validate` 只验证配置；真实引擎评测和本地只读演练分别记录，不能混称为已完成端到端调度验证。
